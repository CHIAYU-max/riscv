# hls4ml baseline for the U-Net block

An HLS-generated accelerator for the same block as the U-Net block benchmark, to put numbers on "When a
loosely-coupled accelerator is the better choice" in `docs/design-notes.md`: what a tool-generated, fixed-function
circuit costs and gains against the RISC-V core with `dot4` / `requant`.

## What is compared

The block of `sw/c/gen_block.py`, with the trained weights of `head.0.block.3` (`BLOCK_WEIGHTS`, first 8 of 32
output channels): a 3x3 convolution on a 6x6x32 u8 tile (4x4 output, s8 weights, int32 bias, 36,864 MACs) ->
per-channel requant (`acc * M / 2^shift`, round half up, clamp to 0..255, which is also the ReLU) -> 2x2 max
pooling. Same input tile (seed 1), same requant parameters, same expected output.

| Design | Generated by | Programmable |
| --- | --- | --- |
| RV32I, software only (`block_ref`) | hand-written core | yes |
| RV32I + `dot4` (`block_dot4`) | hand-written core | yes |
| RV32I + `dot4` + `requant` + `max4` (`block_nn`, `block_rb`) | hand-written core | yes |
| hls4ml, reuse factor 1 / 8 / 32 | hls4ml 1.3.0 -> Vitis HLS 2020.2 | no: one layer shape, weights fixed in the circuit |
| hls4ml, 2:4 sparse weights, reuse factor 1 / 8 / 32 | same | no |

hls4ml writes HLS C++; Vitis HLS turns it into Verilog / VHDL. The comparison is "HLS-generated RTL vs hand-written
SystemVerilog", not "generated SV".

## How the block is mapped to hls4ml

`hls/gen_hls4ml.py` builds a PyTorch model `Conv2d -> BatchNorm2d -> ReLU -> MaxPool2d` with the integer weights and
converts it with hls4ml (`io_parallel`, channels last, Vitis backend, part `xc7a35tcpg236-1`, 10 ns clock):

- Types: input `ap_ufixed<8,8>`, weights `ap_fixed<8,8>`, bias and accumulator `ap_fixed<32,32>`.
- The requant is the BatchNorm, with scale `M / 2^shift` (`ap_ufixed<16+maxshift,16>`, exact), bias 0, mean 0,
  variance 1, eps 0, and result type `ap_fixed<9,9,AP_RND,AP_SAT>`: hls4ml keeps the product at full precision
  (`decltype(a * w)`), `AP_RND` is round half up like `(t + 2^(shift-1)) >> shift`, and the saturation to -256..255
  followed by the ReLU to `ap_ufixed<8,8>` is the clamp to 0..255.
- `fuse_batchnorm` is skipped; folding the requant into the weights would make them non-integer.
- Reuse factor 1 uses the Latency strategy (all multipliers of one output pixel unrolled), larger ones the Resource
  strategy.
- `--sparse24` keeps the 2 largest |w| in every 4 consecutive input channels (1,152 of 2,304 weights zero). That is
  magnitude pruning of the INT8 weights, a stand-in: the INT8 + 2:4 QAT model of the dental project should be exported
  with `sw/export_layer.py` for the real numbers. In a fully unrolled design, zero weights are constants, so HLS
  removes their multipliers; with a reuse factor > 1 the weights sit in an array and the zeros are not free.

## How to run

```
# Windows or WSL, Python with torch + hls4ml 1.3.0 (needs quantizers < 2)
python hls/gen_hls4ml.py --weights build/unet/unet_head0b3.json --out build/hls4ml --rf 1 8 32
python hls/gen_hls4ml.py --weights build/unet/unet_head0b3.json --out build/hls4ml --rf 1 8 32 --sparse24
cp hls/run_soc.sh build/hls4ml/
# copy build/hls4ml to SOC, then
bash run_soc.sh                # csim + csynth per project (in parallel), summary in hls_summary.txt
for p in rf1 rf8 rf32 s24_rf1 s24_rf8 s24_rf32; do
    (cd $p && vivado -mode batch -nojournal -source ../vsynth_ooc.tcl > vsynth.log 2>&1) &
done; wait                     # vsynth_util.rpt, vsynth_timing.rpt per project (about 15 min for all six)
```

(`cp hls/vsynth_ooc.tcl build/hls4ml/` too. hls4ml's own `vsynth=1` did not start Vivado here, and its
`vivado_synth.tcl` has no clock constraint, so `vsynth_ooc.tcl` replaces it.)

`build/hls4ml` holds the trained weights (`firmware/weights`): it stays out of the repository like `build/unet`.

## Results

2026-11-19, hls4ml 1.3.0, Vitis HLS / Vivado 2020.2 on SOC, `xc7a35tcpg236-1` (Basys3: 20,800 LUT, 41,600 FF,
50 BRAM tiles, 90 DSP). C simulation: all six projects bit-exact with the expected output (32 of 32 values).
Area and timing: Vivado out-of-context synthesis (`hls/vsynth_ooc.tcl`, 10 ns clock on `ap_clk`, after
`opt_design`, no place and route). Latency: Vitis HLS C synthesis estimate for one tile (min to max).

| Design | LUT | FF | DSP | BRAM tiles | Latency (cycles) | WNS at 10 ns | Fmax estimate |
| --- | --- | --- | --- | --- | --- | --- | --- |
| rf 1 (Latency) | 102,755 (494%) | 57,270 (138%) | 58 | 0 | 2,313 | -1.56 ns | ~87 MHz |
| rf 8 (Resource) | 52,286 (251%) | 30,661 (74%) | 90 | 26 | 285 - 2,573 | -4.11 ns | ~71 MHz |
| rf 32 (Resource) | 27,867 (134%) | 26,130 (63%) | 82 | 26 | 677 - 2,965 | -2.09 ns | ~83 MHz |
| 2:4, rf 1 | 70,924 (341%) | 42,552 (102%) | 74 | 0 | 2,312 | -0.96 ns | ~91 MHz |
| 2:4, rf 8 | 51,217 (246%) | 29,814 (72%) | 90 | 26 | 285 - 2,573 | -4.06 ns | ~71 MHz |
| 2:4, rf 32 | 29,383 (141%) | 26,104 (63%) | 82 | 26 | 677 - 2,965 | -1.65 ns | ~86 MHz |
| RV32I + `dot4` + `requant` + `max4` (`block_nn`) | to be measured (`make fmax`) | | | | 78,503 instructions | | |

What this shows so far:

- **None of them fits on the Basys3**, even for 8 of the 32 output channels of this one layer; the smallest (rf 32)
  needs 134% of the LUTs. The full layer is 4x larger. This is the "does not fit on a Basys3" of the design notes,
  now with numbers.
- **Speed.** Even the slowest point needs about 26x fewer cycles than `block_nn` (2,965 vs 78,503), at a similar
  clock.
- **2:4 helps only when fully unrolled.** At rf 1 the zero weights are constants and their multipliers disappear:
  LUT -31%, FF -26% (Vivado moves some multipliers into DSPs, 58 -> 74). At rf 8 / 32 the weights are read from an
  array, so zeros cost the same as other weights (LUT -2% / +5%). The same as the dental project's CPU result
  (2:4 is not faster on a CPU): sparsity is only worth something when the hardware is built to skip the zeros.
- **rf 1 is held back by the tool version.** Vitis HLS 2020.2 ignores the partition of the input array `x`
  (`HLS 214-250: Ignore array partition/reshape applied to 'x' in struct`), so the input has only two memory ports
  and each output pixel waits 144 cycles for its 288 inputs (16 pixels x 144 = 2,304). With the partition applied
  (newer Vitis HLS), rf 1 should finish in tens of cycles and be even larger.
- The rf 8 / 32 latency range comes from the Resource strategy's `PartitionLoop` (40 to 183 cycles per pixel).
  Vitis HLS 2025.2.1 (local, WSL) schedules rf 32 to a fixed 670 cycles.
- C/RTL co-simulation (Verilog): the RTL output of all six is identical to the expected output (files compared
  2026-11-21; the report's "Pass" alone does not show this).

### Design points that fit (2026-11-19, same tools)

| --- | --- | --- | --- | --- | --- | --- | --- |
| `io_parallel`, rf 144 | 29,146 (140%) | 25,910 | 20 | 9 | 2,533 - 4,821 | -2.77 ns | ~78 MHz |
| `io_parallel`, rf 288 | 26,510 (127%) | 21,196 | 9 | 4 | 4,788 - 7,076 | -3.89 ns | ~72 MHz |
| `io_stream`, rf 32 | 3,945 (19%) | 6,302 (15%) | 75 (83%) | 14 | 1,486 - 1,513 | +2.13 ns | ~127 MHz |
| `io_stream`, rf 144 | 3,234 (16%) | 5,746 (14%) | 20 (22%) | 8 | 5,342 - 5,473 | +0.33 ns | ~103 MHz |

All four bit-exact in C simulation and in RTL co-simulation (output files compared 2026-11-21).

- With `io_parallel` the reuse factor hardly matters past 32: the LUTs are in the fully partitioned 1,152-byte
  input, the im2col multiplexers and the output, not in the multipliers.
- **`io_stream` (line buffer) is the design point to compare with the core**: it fits with room to spare, meets
  100 MHz, and a stream interface is what a coprocessor next to the core would have. rf 32 is DSP-bound (75 of 90),
  rf 144 leaves DSPs for the core.
- Against `block_nn` (78,503 instructions): about 52x fewer cycles for `io_stream` rf 32 and 14x for rf 144, for
  one layer shape with the weights built in.

### `io_stream` with Vitis HLS / Vivado 2025.2.1 (2026-11-20, local WSL, the version `make fmax` uses)

**Not valid: the RTL computes wrong results (found 2026-11-21).** C simulation is bit-exact, but the RTL
co-simulation output differs from the expected output in all four projects below (and in all six whole-layer
projects, with and without forced DSPs). The co-simulation report says "Pass" because hls4ml's test bench does not
compare anything; the comparison is hls4ml's `validation` step, which `hls/run_local.sh` had switched off. The same
`io_stream` projects built with Vitis HLS 2020.2 on SOC give RTL outputs identical to the expected ones (compared
2026-11-21, together with every other 2020.2 project), and `io_parallel` rf 32 with 2025.2.1 is also correct, so
the fault is in Vitis HLS 2025.2.1's handling of the `io_stream` design (cause not found yet). The numbers below are
kept only as a record; use the 2020.2 numbers. `hls/run_local.sh` now runs the validation step.

| Design | LUT | FF | DSP | BRAM tiles | Latency (cycles) | WNS at 10 ns | Fmax estimate |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `io_stream`, rf 32 | 11,476 (55%) | 9,929 (24%) | 8 | 13 | 1,487 - 1,513 | +1.33 ns | ~115 MHz |
| `io_stream`, rf 144 | 6,608 (32%) | 8,461 (20%) | 4 | 7 | 5,337 - 5,473 | +0.37 ns | ~104 MHz |
| 2:4, `io_stream`, rf 32 | 11,620 (56%) | 10,002 (24%) | 8 | 13 | 1,487 - 1,513 | +1.33 ns | ~115 MHz |
| 2:4, `io_stream`, rf 144 | 6,750 (32%) | 8,534 (21%) | 4 | 7 | 5,337 - 5,473 | +0.37 ns | ~104 MHz |

All four bit-exact in C simulation (32 of 32); the RTL output is wrong (above).

- **2025.2.1 builds the 8-bit multipliers from LUTs instead of DSPs**: rf 32 goes from 75 DSP / 3,945 LUT (2020.2)
  to 8 DSP / 11,476 LUT, with the same latency. Which one to report depends on how the core's `dot4` is mapped;
  forcing DSPs (`config_op mul -impl dsp` or a `BIND_OP` pragma) would make the two comparable either way.
- **2:4 gives nothing with `io_stream`** (+1-2% LUT): the weights are read from arrays, so a zero weight costs the
  same as any other. Real 2:4 QAT weights would not change that; only a fully unrolled design (or hardware that
  stores and skips the zeros) gains from sparsity.
- Latency is the same as with 2020.2, so the 2020.2 cycle counts above hold.

### Whole layer: 32 of 32 output channels on the Nexys A7 and ZedBoard parts (2026-11-21)

The same tile (6x6x32 input, 4x4 output) with all 32 output channels of `head.0.block.3` (147,456 MACs per tile).

file) into `build/unet/unet_head0b3_cout32.json`. `io_stream`, Vitis HLS / Vivado 2020.2 on SOC

- **2020.2 already puts the 8-bit products in DSPs**, so forcing DSPs changes almost nothing (at most 2 DSP and
  1,000 LUT). The open question of matching 2025.2.1's LUT multipliers is moot, since that version's RTL is wrong.
- **rf 32 takes every DSP on both parts** (288 multipliers needed) and builds the rest from LUTs. It still fits
  (26% / 34% of the LUTs), but leaves no DSP for the core; rf 72 leaves about 90 / 70 DSPs.
- **Throughput.** rf 32 does the 147,456 MACs of a tile in about 1,500 cycles, about 98 MACs per cycle, the same
  latency as the 8-channel design with 4x the work. Against `block_nn` (0.47 MACs per instruction on the 8-channel
  tile) that is about 200x per cycle.
- **One whole layer at 512 x 512** (about 2.4 G MACs) at 100 MHz: about 0.25 s with rf 32, 0.5 s with rf 72,
  1 s with rf 144 (from the per-tile rate; streaming a 512-wide image needs larger line buffers, about 2 rows x
  514 x 32 bytes, roughly 9 more 36 Kb block RAMs, not in these numbers).
- Out-of-context synthesis, no I/O and no AXI wrapper, as above.

## Notes on the tools

- The local Vivado / Vitis 2025.2.1 has no Zynq-7000 device support installed (`Part 'xc7z020clg484-1' is not
  installed`); the ZedBoard numbers come from SOC. Installing the Zynq-7000 devices locally (Vivado installer,
  "Add Design Tools or Devices", needs an AMD account) is needed before the ZedBoard bring-up anyway.
- Always compare the RTL output with the expected output (hls4ml's `validation` step, on in `hls/run_local.sh` and
  `hls/run_soc_cosim.sh`); the co-simulation report's "Pass" only means the simulation ran.
- Vitis HLS 2020.2 (on SOC) is older than what hls4ml 1.3.0 targets; `config_array_partition -maximum_size` is not
  supported there (hls4ml wraps it in `catch`), the rest of the flow ran.
- hls4ml 1.3.0 with `quantizers` 2.0.0 fails to import (`get_fixed_quantizer_np`); `quantizers` 1.2.2 works.
- The clock uncertainty defaults to 27% (2.7 ns of 10 ns), so the HLS timing estimate is conservative; the Vivado
  synthesis numbers are the ones to compare with `make fmax`.
- Out-of-context synthesis has no I/O: `io_parallel` with `ap_vld` ports puts the whole 1,152-byte input and the
  32-byte output on ports, which a Basys3 board design could not do. A board design would need `io_stream` or an AXI
  wrapper, which adds area that is not in these numbers.

- hls4ml's `build_prj.tcl` does not read command-line options, only `build_opt.tcl` (defaults: csim, synth, cosim
  and validation on, vsynth off). `hls/run_local.sh` rewrites it.
- Vitis 2025.2.1 is installed in WSL (`/Xilinx/2025.2.1`, the version `make fmax` uses): run it with
  `vitis-run --mode hls --tcl build_prj.tcl` (`hls/run_local.sh`). With WSL limited to 6 GB (`.wslconfig`), the
  fully unrolled rf 1 projects ran out of memory during scheduling; `io_stream` and rf 32 run fine.
- rf 1 with Vitis HLS 2025.2.1 (2026-11-19 22:30, WSL at 10 GB): C simulation bit-exact, but the scheduler was
  still on `PartitionLoop` after 12 hours (one core at 100%, 1.3 GB resident; memory was not the limit). With the
  input partition applied, the fully unrolled 2,304-multiplier loop is more than the scheduler handles in
  reasonable time, so rf 1 stays at the 2020.2 numbers (marked as limited by the ignored partition).
